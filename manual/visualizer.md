# `visualizer/` の使い方

対象: [`visualizer/`](../visualizer/)

取得、探索、送信をGUIから操作し、マップやJSON、実行ログを確認するためのデスクトップアプリである。各段階を手動で開始して日次回答の送信方法を手動／探索後自動から選べるほか、「試合終了まで全自動」で問題公開待ちから最終日の回答送信まで継続できる。3人運用では、先行担当の短時間解を自動送信し、追走2人がより良い解だけを手動送信できる。

ビーム幅は既定で自動選択され、盤面サイズ・当日のステップ数・台数で切り替わる。手動幅を使う場合は「探索パラメータ」の「ビーム幅の自動選択」を0にする。

```sh
python3 visualizer/app.py
```

macOSのシステムPythonが古いTk 8.5を使用する場合は、対応するTkを持つインストール済みPythonへ自動で切り替える。`python3 visualizer/app.py --check-runtime`で選択されたPythonとTkを確認できる。詳しくは[`runtime.py`](visualizer/runtime.md)を参照。

詳しい操作順と生成物は[`visualizer/README.md`](../visualizer/README.md)を参照する。

アプリアイコンは白背景・黒線のベンゼン環で、編集用SVGとTk表示用PNGを`visualizer/assets/`に置く。詳細は[`app.py`](visualizer/app.md)を参照する。

## ファイル別マニュアル

- [`app.py`](visualizer/app.md): 画面構成、試合操作、簡易サーバー操作
- [`backend.py`](visualizer/backend.md): 通信・ソルバー・簡易サーバー・チェックポイント管理
- [`runtime.py`](visualizer/runtime.md): macOSでのPython/Tk実行環境選択

メイン画面の「実行設定・使用ファイル」から専用ウィンドウを開き、TOKEN欄を直接編集して「通信確認（手動）」を押すと、GETで接続を確認できる。起動だけでは通信しない。トークンは入力欄では通常表示し、GUIログでは伏せる。

実サーバーを使わない確認では、画面上部の左端にある「簡易サーバー」チェックを入れ、右側に表示される設定でJSONとチームを選んで「起動して使用」を押す。URL、TOKEN、作業フォルダがローカル確認用へ切り替わり、以降は通常と同じ操作を使える。種別締切はサーバー起動時から進むため、余裕のある秒数を設定する。停止ボタンまたはGUI終了で子プロセスを停止する。新しい試合で同じ保存先を使う場合は、停止中に「作業フォルダをクリア」を押す。実サーバー用`.env`は上書きしない。

通常の個別運用では「mainを最適化ビルド」を手動で押し、「問題公開待ち・設定取得・種別選択・送信」で初期設定をまとめて実行する。各日は「状態公開待ち・取得・探索」を押す。日次回答はボタンで確認して送るか、探索成功後の自動送信を選ぶ。初回取得後は「探索」へ切り替わり、同じ日の開始状態で再探索できる。送信後も対象dayを維持し、日終了時刻を過ぎると翌日に進む。翌日の初回取得・探索は再びボタンで始める。対象dayの範囲は試合設定の日数に合わせる。

第1試合の3人運用では、担当1が問題公開待ちからエージェント選択・送信、全日の探索・回答送信までを全自動で行い、担当2・3は設定だけを取得する。エージェント種別は初期・中間・最終の3段階とし、第1試合50秒、準決勝80秒、決勝110秒まで探索する。第1試合は予行演習と同じ16×16・5日等の条件で、エージェント回答・行動回答だけが各60秒になる。担当1・2は`--udon-sa 0`のビーム系探索、担当3は`--udon-sa 1`の焼きなましを使う。時間上限は10,000 / 40,000 / 50,000 msで、5秒の安全余裕を除いた探索目安は約5 / 35 / 45秒である。担当2・3は時計の左にある`系列数 / 総系列数 / 玉数`を口頭で比較して、改善時だけ手動送信する。探索終了時に画面上部へ表示される`系列mask 玉数 日別系列累計`は候補比較にも使い、採用回答のHTTP 200受理後だけ他端末へ読み上げる。他端末は次の対象dayを選び、下段へ1行入力してEnterする。取込成功時だけ入力欄を空にし、エラー時は入力を残す。最終日の回答後は取込不要と案内してファイルを作らない。全自動ボタンは担当1と通常モードで有効、担当2・3では無効にする。

準決勝24×24・5台と決勝32×32・7台は、3人運用を選ばず通常モードを1人・1端末だけで使用する。追走端末、口頭チェックポイント共有、共有入力欄は使わない。画面上部の試合区分を準決勝または決勝へ切り替えると、エージェント選択時間が90秒または120秒、日次回答時間が60秒に設定される。設定取得後は、準決勝なら6日、日別ステップ`48,56,68,68,56,72`、24スポット、18系列、最大在庫合計60、燃料80、混雑1、渋滞2、決勝なら32スポット・20〜28系列を含む公式既知条件との一致も確認する。ソルバー側は長時間SAの停滞後も残時間があれば独立拡張パスを比較し、系列数を落とす回答へ置き換えない。

担当選択後の「mainを最適化ビルド」は、`-O3 -DNDEBUG`の共通バイナリを作成できる。担当ごとの差はビルドフラグではなく、GUIが同時に反映する時間上限、自動ビーム幅、`--udon-sa`の実行時引数で決まる。

1番ボタンは担当1なら1b、担当2・3なら1aへ自動で切り替わる。口頭入力時の`nextDay`はGUIの対象dayから自動生成される。有線LAN、共有フォルダ、共有コードの設定は不要である。

「探索パラメータ」タブでビーム幅、同時行動幅、スレッド数、時間上限、マクロ行動、種別選択試走などを指定できる。C++側は[`solver_options.hpp`](inc/solver_options.md)で引数を読み取る。既定の種別選択は補給車を少なくとも1台含める。処理中も画面は応答し、当日状態の取得ごとにマップとエージェント・スポット表を更新する。マップ上部には盤面寸法、day、日数、当日ステップ数、エージェント数、スポット数、重複なし系列数、燃料上限を表示する。エージェント表はID、P/S、`pos(x,y)`形式の位置、燃料、現在/上限ステップを、スポット表は在庫を残数/初期数で表示する。探索完了時は各車の移動経路を色分けして表示し、次の日の探索開始時に消す。ローカル設定の探索後は、右側の状態表も終了時の位置・燃料・ステップ・残在庫へ更新する。

設定を読み込むか対象dayを変えると、その日の`daySeconds`が探索時間上限へミリ秒で入る。必要なら探索前に短い値へ変更できる。ランダム生成の初期値は16×16、4エージェント、16スポット、14系列、10日で、混雑・渋滞の有無を指定できる。seedはGUIでは指定せず生成ごとに新しく選ぶ。生成できるマップは[`sample_maps/README.md`](../sample_maps/README.md)の3区分に限り、行動回答時間は60秒固定。JSONタブは単純な配列・オブジェクトを1行にまとめ、入れ子配列を配列単位で改行するため、`answer.json`は1エージェントの経路が1行になる。

簡易サーバーを使う場合も先に`main`をビルドする。サーバーを起動した時点から種別締切の時計が進むためである。起動後の成果物は`runtime/simple-server/client/`、サーバーログは`runtime/simple-server/simple-server.log`へ保存する。
