# `brain/brain1.hpp` の使い方

対象: [`inc/brain/brain1.hpp`](../../../inc/brain/brain1.hpp)

全エージェントの1日分の行動計画をビームサーチと系列補完探索で生成するソルバー本体である。

## 基本的な呼び出し

```cpp
benzen::BeamSearchConfig config;
config.beamWidth = 128;
config.jointBeamWidth = 512;
config.timeLimitMs = 2500;

benzen::ScoreState previousScore;
auto result = benzen::brain1(
    setting, matchState, previousScore, config);

if (result.success) {
    const benzen::DailyPlan& plan = result.plan;
}
```

## 主要設定

- `beamWidth`: 各展開で残す状態数
- `refineBrands`: 系列補完を有効化。既定true
- `brandSearchNodeLimit`: 系列補完の状態展開上限。既定10000
- `exactBrands`: 補完の状態展開上限を解除。締切は維持。既定false
- `useBrandRepair`: 未獲得系列を対象とした連鎖再計画。既定true
- `brandRepair`: 局所探索の試行数（16）、各試行の展開上限（1000）、巡回車数（2）。詳細は[系列救済](../brand_repair.md)
- `jointBeamWidth`: 同時に空いた複数台へ行動を割り当てる途中幅
- `timeLimitMs`: 相対時間制限。0なら指定なし
- `useStateDeadline`: `MatchState::endsAt`も締切に使う
- `safetyMarginMs`: 締切前に残す余裕
- `iterativeDeepening`: 固定幅の探索が早く完了したとき、残り時間でビーム幅・行動候補・合流候補を段階的に広げて再探索。既定true
- `threadCount`: 0で自動、1で並列無効
- `maxActionsPerAgent`: 各台で残す合法行動数。0で全候補
- `useMacroActions`: スポットや合流点への経路をまとめて生成
- `macroReplanInterval`: マクロ継続と別経路を併せて検討する間隔。既定0は定期再検討なし。在庫切れの目的スポットは間隔によらず再検討する
- `comparePeriodicReplanPlans`: 盤面サイズ・台数によらず、十分な探索時間がある最終日に既定経路と4イベントごとの定期再計画経路を比較し、公式得点を優先して高い方を採用。公式得点が同じ場合は終端評価で比較。既定true
- `routePortfolioMinTimeMs`: 経路方式を比較する最小相対時間。既定5000ms
- `reassignStalePatrolRoutes`: 共同割当の変化で旧巡回先の在庫が予約済みになった場合や、より重要な系列が割り当てられた場合に再計画候補も生成。既定true
- `simplifySupplyRoutes`: 探索後、最終状態を変えない補給車の周回移動を待機へ置換。既定true
- `allowUnassignedSupplyMoves`: 24×24以上で合流未割当の補給車に自由移動を許す検証用フラグ。既定falseでは、目的地を持つ巡回車のうち燃料が最も少ない1台へ近づく移動だけを優遇する
- `coordinatedAssignments`: 補給車の競合で合流できない巡回車の目的地を再割当。既定true
- `detourRendezvous`: 通常の経路上で合流できない場合、迂回合流も検討。既定true
- `detourCandidateLimit`: 燃料制約付き実経路を確認する迂回候補数。既定6
- `finalDayDetourCandidateLimit`: 翌日配置とのトレードオフがない最終日に確認する迂回候補数。既定8
- `exhaustFeasibleDetours`: 燃料制約が厳しい場合、到達不能な迂回候補を確認数上限へ含めず次候補を調べる。既定true
- `twoSpotLookahead`: 取得後の残時間・残燃料で次の1店に到達できることを割当の誘導値に使用。既定true
- `prioritizeHardNextDayTargets`: 32x32以上の軽交通・燃料制約下で、最終日前日に遠隔の一意系列へ巡回車を寄せる。既定true
- `lookaheadCandidateLimit`: 距離順で調べる2店目候補数。既定6
- `assignmentCacheLimit`: 日次探索内の割当キャッシュ件数上限。既定4096、0で無効
- `profilePlanning`: 割当・最小費用流・合流計算の時間を計測する。既定false。計測は負荷を加えるため速度比較ではオフにする
- `dominancePruning`: 燃料優越状態を削除
- `diversityFraction`: 異なる系列・位置へ確保するビーム割合
- `weights`: `EvaluationWeights`

## 結果

`BeamSearchResult`には計画、最終状態、評価内訳、展開数、評価回数、マクロ統計、補給車から除去した周回数`removedSupplyLoops`、経過時間、停止理由が入る。`success == false`の場合は`plan`を送信せず、`application.hpp`の`solveDay()`などで待機計画へフォールバックする。

公開入口`brain1()`はビーム探索後に`brand_repair.hpp`で系列救済型の連鎖再計画を行い、その後`brand_search.hpp`で全車の系列を補完する。有限時間では安全余裕を除いた予算の80%をビームへ渡し、ビーム終了後の残り時間の75%を連鎖再計画へ、残りを全車探索へ渡す。全車補完は6方向移動と1ステップ待機を列挙し、補給・在庫競合・移動中取得を公式シミュレータで判定する。燃料を緩和した最短時間で系列上限を求め、現解を超えない状態と完全に等価な状態だけを捨てる。長時間待機は1ステップ待機の反復で表現できるので、行動候補の打切りはない。`brandRepairAttempts`、`brandRepairExpanded`、`brandRepairImprovements`で連鎖再計画の統計を確認できる。`exactBrands=true`では連鎖再計画を省略する。

`brandOptimal=true`は、指定種別・当日交通に対する「当日終了時の試合系列数、当日系列数」の辞書順最大値を証明したことを表す。上限達成または全探索完了で証明する。`matchBrandUpperBound`と`dailyBrandUpperBound`は系列上限、`brandSearchExpanded`は補完の状態展開数。上限未達で時間・展開数上限に達した場合は`brandOptimal=false`を返し、得られた合法な最良計画を保持する。補完は系列数が厳密に改善した場合だけ計画を置換する。同系列数の玉数や翌日配置の最適化はビーム側が担当する。全日・種別選択の大域最適性はこの証明の対象外。

`distanceCacheEntries`（既定8、上限8、0で無効）は同一地形・交通条件の距離表を呼び出しスレッド内で再利用する。寸法、地形、各セルの移動時間、順序を含むスポット位置を完全比較し、最も長く使っていない条件から破棄する。中断した前計算、割当状態、得点、締切のコールバックは保存しない。`reusedDistanceTables`で再利用の有無を確認できる。時間制限なしではキャッシュ有無で回答は変わらない。

`assignmentCacheHits`と`assignmentComputations`は割当の再利用・計算回数、`repairedAssignments`は競合で除外した巡回先の数、`detourPlans`は計算した割当結果に含まれる迂回合流の数を表す。実際に最終回答へ採用された回数ではない。

探索が生成して再シミュレーションした合法な完了計画の選択では、全日で試合系列数、次に日別系列累計を終端ヒューリスティックより優先する。中間日は系列数が同じ場合、翌日配置を含む終端評価で比較し、当日の獲得数だけを増やして翌日の系列を失う計画を避ける。最終日は翌日がないため、系列数が同じ場合も獲得数、終端評価の順で比較する。これは探索済み候補間の系列数非退行を保証するが、時間・燃料・地形上不可能な系列や、ビーム幅・締切で生成されなかった経路まで含む大域最適性を保証するものではない。

`comparePeriodicReplanPlans`による経路方式比較は公開入口`brain1()`で行う。最終日、マクロ有効、`macroReplanInterval == 0`で、相対上限が`routePortfolioMinTimeMs`以上または締切のない無制限探索の場合だけ有効になる。有限時間では通常経路へ実効予算のおよそ半分を割り当て、残時間で4イベント周期再計画経路を探索する。最終日は翌日評価が不要なので、周期再計画経路の公式得点が高ければ終端ヒューリスティックにかかわらず採用し、公式得点が同じ場合だけ終端評価で比較する。探索内の完了計画と最終ビームも、系列数を全日で最優先する。小・中盤面でも定期再計画による系列・獲得数の改善が確認されたため、盤面サイズと台数による制限は設けない。

方式比較時の`elapsedMs`は両探索を含む壁時計時間で、展開数、評価回数、マクロ候補、割当・合流統計は両探索の合計になる。`Brain1::search()`を直接呼ぶと方式比較は行われないため、通常の呼び出し側は`brain1()`、`application.hpp::solveDay()`、`match_runner.hpp::runMatch()`を使用する。中間日の位置を変えて後日の系列数を下げることを避けるため、方式比較は最終日に限定している。

`profilePlanning=true`の場合、`assignmentTimeNs`、`flowTimeNs`、`rendezvousTimeNs`を返す。割当時間はキャッシュミス後の共同割当計算時間、最小費用流は最短増加路の実行時間（翌日目的地評価分も含む）、合流は実計算時間を表す。計測範囲が重複するため、3つを加算して総時間としてはならない。並列時は各スレッドの時間を合計し、壁時計時間とは区別する。

結果は内部でも検証されるが、外部から組み替えた計画は`validateDailyPlan()`で再検査する。

補給込み経路は1回の合流で目的地まで届かない場合、到達可能な合流点でマクロを区切る。補給反映後に次の合流点を再計算するため、同じ日・同じ目的地までに複数回の補給が必要な経路も扱える。

探索完了後は、補給車が移動して同じセルへ戻る区間を長いものから待機へ置換する。置換のたびに全エージェントの計画を公式順で再シミュレーションし、位置・燃料・取得・在庫・得点を含む最終状態が元と完全一致する場合だけ採用する。実際の合流に必要な移動や、巡回車の燃料・取得結果を変える周回は残す。送信余裕を消費し過ぎないよう、再シミュレーションは1探索につき最大128回に制限する。

合流割当は必須の補給と未取得系列を優先し、目的スポットへの到着時間、巡回車の待ち時間、補給車の移動時間で比較する。直接到達できる巡回車には、目的スポットへの到着を遅らせる任意の補給を割り当てない。マクロの目的スポットが在庫切れになった場合は、元の経路の継続に加えて新しい目的地への候補を生成する。巡回車の共同割当が別スポットへ変わり、旧目標の在庫が他車の予約だけで埋まる場合や、新目標の系列優先度が高い場合も、元経路を残しつつ再計画候補を生成する。補給車のマクロ継続時は現在の一対一割当も確認し、別の有効な合流地点へ割当が変わっていれば古い経路固定を解除する。割当が一時的に見つからないだけの場合は経路を維持し、補給車が再計画だけを繰り返すのを避ける。

24×24以上で補給車に有効な合流割当がない場合、候補移動を一律に待機より高く評価しない。目的地を持つ巡回車のうち予測燃料が最も少ない1台を選び、その車との交通時間を短縮する移動だけを優遇する。距離を維持・増加させる移動は待機より低く評価し、無目的な横移動を抑えつつ次の補給への先回りを残す。小盤面では自由移動による先回りが日別系列を改善するケースがあるため、この制限を適用せず終端状態一致による周回除去だけを行う。

複数の補給車がある場合、一対一合流割当の競合で日開始直後だけ特定の補給車から合流先が消えることがある。この状態で「残り時間すべて待機」を予約すると、巡回車の移動完了後も割当を再計算できない。24×24以上では最初の約1/32日かつ補給車が複数台の場合だけ長時間待機を候補上位から外し、1ステップ待機後に合流を再評価する。補給車1台の問題と日中盤以降は従来どおり待機を許す。

緊急の合流候補がない場合も、補給車が巡回車より遅れずに次の目的スポットへ到着できれば、そのスポットを待機合流点にする。巡回車の直接経路は変えず、補給車だけを先回りさせる。待機合流も通常の合流と同じ一対一割当に含めるため、1台の補給車を複数の巡回車へ同時に割り当てない。複数の先回り候補がある場合は、到着後に次の有望スポットへ進むための燃料不足も割当の優先度へ加える。巡回車が目的地で燃料0になる場合は、現在の残燃料が半分以上でも事前補給を検討する。先回り用の直接経路と継続燃料の計算は巡回車ごとに一度だけ行い、補給車ごとに再計算しない。

巡回先を仮割当した後、補給車を一対一で割り当てる。直接到達も合流もできない車の巡回先を禁止し、巡回先と合流を再計算する。反復はエージェント数に応じて制限するため、全巡回順・全補給時刻の厳密な同時最適化ではない。

迂回合流では到着時間の下界で候補を並べる。経路上の合流が成立していても目的地への最短到着時刻より遅ければ、さらに早い迂回合流を比較する。既存案の改善では事前計算済み最短路を復元し、現在の燃料・残時間で合流地点まで到達できる候補だけを採用する。合流案がない場合は燃料節約経路も燃料制約付き探索で調べる。いずれも補給車の到着時刻と、合流後に満タンで目的地へ到達できる経路を確認する。検査数に上限があり、迂回を含む複数回補給の最適性は保証しない。2店目の先読みも他車との2店目の在庫競合までは予約しない誘導値であり、実際の取得・燃料・補給はシミュレータで検証する。

割当キャッシュは各`brain1()`呼出しに閉じ、設定や当日交通が異なる探索間では共有しない。位置・燃料・予約・在庫・取得履歴・得点・時刻を含む正規化済み状態を完全比較し、ハッシュ衝突だけで別状態を同一視しない。容量上限で消去する。実効スレッド数が2以上の場合だけmutexで並列アクセスを保護し、1スレッドでは高頻度なキャッシュ参照・保存の不要なロックを省く。時間制限なしの回帰試験でキャッシュ無効・容量1・直列／並列時の計画一致を確認する。

共同割当の1回の計算内では、巡回車・スポット・補給車をキーとして合流結果を再利用する。位置・燃料・予約・残時間が固定された区間だけで使い、次の状態の割当計算前には初期化する。補給車1台の場合は「任意の補給車」と「その補給車」の要求を同一視できる。複数台の場合は候補数制限の違いを保つため同一視しない。

最小費用流の辺・FIFO・最短路バッファはスレッドごとに再利用する。通常燃料の迂回合流候補は全件ソートせず、同じ比較順で検査する上位候補だけを`partial_sort`で求める。燃料上限が初日ステップ数以下の場合は最小ヒープから下界順に取り出し、合流点へ実際に到達できない候補を`detourCandidateLimit`へ数えず次候補を確認する。燃料・時間の下界で不可能な経路は先に除外する。

ビーム内の重複状態判定は、ハッシュごとの候補順を保つ連続した表で処理し、作業配列を呼出しスレッド内で再利用する。評価時の到達可能スポット検査は割当先がなく、待機もできない場合だけ行う。これらは探索幅や採用順を変えず、固定探索量で同じ計画を返すことを回帰試験で確認する。

行動候補はゲーム状態全体ではなく、その車の予約行動と評価値・経路情報を保持して選別する。評価用の状態は親ごとに1回だけコピーし、採用候補の予約だけを子状態へ反映する。候補配列も探索内で再利用し、各行動での大きな状態コピー・ソート時の移動・メモリ確保を削減する。

既存案より早くならない候補は到着時間の下界で除外し、候補評価中に改善した場合もその境界を更新する。同時刻なら、追加補給を必要とする案より1回の補給で到達できる案を優先する。追加改善に燃料節約経路の網羅探索は行わず、候補数上限も維持するため、最適な合流点を保証するものではない。

全地形・交通で1移動の時間が消費燃料の2倍以下であることから、最短移動時間が残燃料の2倍を超える合流地点は事前に除外する。この必要条件で除外した地点は`detourCandidateLimit`を消費せず、残り候補を実経路で検証する。

翌日配置は通常、近い未取得系列への進捗を評価する。最終日前日の32x32以上で、
道路影響が10%以下、翌日の燃料上限がステップ数の1.2倍以下の場合に限り、
店舗が1つしかなく全巡回車から翌日ステップ数の4分の1以上離れた系列を
難所として追加優先する。小中盤面、混雑・渋滞が広い日、燃料に余裕がある問題では
従来の近距離配置を維持する。
