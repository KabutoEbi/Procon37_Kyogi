# `agent_selector.hpp` の使い方

対象: [`inc/agent_selector.hpp`](../../inc/agent_selector.hpp)

試合開始前に、各エージェントを巡回車または補給車へ自動割当する。

```cpp
benzen::AgentSelectorConfig config;
config.minSupplyCount = 1;
config.maxSupplyCount = 2;
config.trialCandidateLimit = 12;
config.trialDays = 0; // 全日試走

auto selected = benzen::selectAgentKinds(setting, config);
if (selected.success) {
    const std::vector<benzen::AgentKind>& kinds = selected.kinds;
    // kindsを試合開始時のPOST /agentやrunMatch()へ渡す
}
```

最初に全配置を到達範囲、各巡回車が回れる近いスポット、補給距離で評価する。到達系列数、日別到達系列数、理論獲得数はいずれも初日だけでなく全日程の`daySteps`を使う。獲得量はスポット在庫をそのまま足さず、巡回車ごとの同一スポット1日1回制約と各日の行動数で上限を取る。これにより、短い初日だけへの過適合と、補給車を増やした候補へ巡回車では取得できない在庫分まで加点する問題を避ける。

公開試合150件の上位結果から推定した構成傾向は弱い事前分布として使う。中心は4台で巡回3・補給1、5台で3・2、7台で5・2であり、「補給車1台で巡回車およそ2台」の一般式で表している。中心から外れる候補には小さなペナルティを与えるが、到達系列を減らすほど強くはせず、巡回車追加による理論獲得数の差が大きい盤面では巡回寄りを選択できる。

補給車の台数ごとの最良配置と、補給車を離して置く配置を確保し、残りの候補枠は中心台数と、その1台少ない構成へ重点配分する。台数比較はこの中心台数から近い順に行い、7台なら補給2台、次に1台・3台を試す。その後で各台数の広域配置と位置違いを比較する。これらを`brain1`で複数日・複数交通シナリオ試走する。既定の試走候補数は12である。既定の交通シナリオは設定のチーム数・エージェント数と道路閾値から予測した低位・中央・高位条件である。候補はシナリオの合計スコア、次に最悪スコアで比較する。既定では全日を試走し、補給車を最低1台、巡回車を補給車以上残す。したがって3台の場合は巡回車2台・補給車1台になる。

## 主な設定

- `minSupplyCount`, `maxSupplyCount`: 補給車台数の範囲。既定の最小は1、最大`-1`では全台数の半分（切り捨て）が自動上限。明示値では半数超も指定可能
- `trialCandidateLimit`: 試走する初期候補数。`extendTrialsToDeadline == false`では厳密な上限。0なら距離評価だけ
- `trialBeamWidth`, `trialJointBeamWidth`: 試走用探索幅
- `trialDays`: 試走日数。0なら全日
- `trialScenarioCount`: 予測交通量から自動生成するシナリオ数
- `trialScenarios`: 明示的な交通条件
- `timeLimitMs`: 種別選択全体の相対時間制限
- `deadlineUnixSeconds`: 明示的に分かっている種別締切のUNIX時刻
- `safetyMarginMs`: 締切前に残す余裕
- `extendTrialsToDeadline`: 時間制限がある場合、初期候補の完了後も未試走配置を締切まで追加比較。低レベルAPIの既定はfalse、CLIはtrue

結果には選択種別、補給車数、評価候補数、試走回数、最悪・合計試走スコア、`timedOut`が入る。試走候補の作成後に完走候補がない場合は中心台数の最良構成を返す。距離表を作り終える前に締切となった場合も、先頭の車両を機械的に補給車にはせず、スポットと他車の開始位置に対する幾何距離を使った軽量な配置評価で、中心台数の補給車を選ぶ。燃料上限が最長日の行動数以下で、試走が時間切れし、選択結果が中心台数より少ない場合は、到達可能系列数を落とさないことを確認して中心台数の広域配置へ切り替える。これにより短い締切で補給1台や不利な開始位置へ偏るのを防ぐ。設定不整合は`std::invalid_argument`になる。

短い締切でも台数比較を失わないよう、中心台数から近い順に各台数の最良配置を試す。続いて各台数の広域配置、中心となる補給台数の位置違いを試す。CLIではその後も未試走配置を追加し、全配置の比較完了または締切まで続ける。距離表を再利用して複数日・複数シナリオの試走を進め、試走全体の残り時間は各日の開始時に再配分する。

種別候補間で同じ探索量を使うため、試走中は`brain1()`の最終日経路方式比較を無効にする。選択された種別で本探索を行う場合は、日次ソルバー側の設定条件に応じて経路方式比較を使用できる。

同じ候補の交通シナリオでは、初日から道路状態が連続して一致する日まで、直前の試走結果を再利用する。交通条件が分岐した日以降は個別に探索する。各開始位置の近い3スポットによる巡回能力は、全日程で到達可能性を平均し、全配置で共通なので1回だけ計算する。

`completedTrialScenarios`は選択に採用した候補が完走したシナリオ数である。全指定シナリオを完走した候補だけを比較し、未完走候補の部分的な得点は採用しない。`trialAssignments`と`trialSimulations`は着手件数なので、完走数とは異なる。日次探索は時間内の最良有効解を使用し、「試走完走」は指定日数のシミュレーション完了を意味する。

交通予測は試合開始前に分かる集計値だけを使う。エージェント数が多いほど予測平均を高くし、チーム数が多いほどチーム平均の予測幅を狭くする。実際の他チームの種別・目的地・経路は不明なので、道路ごとの結果は確定値ではない。試合開始後の日次探索では予測を使わず、APIから配布された当日の道路状態を使う。

混雑・渋滞を含む8台の再比較では、シナリオ合計を優先する既定比較が、最悪シナリオ優先より未使用交通条件の玉数で上回った。距離による候補抽出へ予測交通を混ぜても選択と得点は変わらなかったため、候補抽出は順調時の地理的な到達性、試走は複数交通条件という分担を維持している。比較値は[混合交通での再計画・種別選択記録](../tests/mixed-traffic-reroute-results-2026-09-30.md)を参照。

32×32・7台・32スポット・20系列の時間切れ対策と混合交通での結果は[2026-10-02の種別選択改善記録](../tests/agent-selection-traffic-results-2026-10-02.md)を参照する。
