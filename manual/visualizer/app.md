# `app.py` の使い方

対象: [`visualizer/app.py`](../../visualizer/app.py)

Tkで取得・探索・送信を操作するGUIの入口である。リポジトリ直下から起動する。
アプリアイコンには白背景・黒線のベンゼン環を使用し、`visualizer/assets/app_icon.png`を起動時に読み込む。編集用のベクター原稿は同じ場所の`app_icon.svg`である。

```sh
python3 visualizer/app.py
```

Windowsでは`py -3 visualizer/app.py`で起動する。ソルバーの既定パスは
`main.exe`となり、GUIビルドはMinGW、Clang、Developer PowerShellのMSVCに
対応する。CMakeを使う場合はリポジトリ直下の`build-windows.ps1`を実行する。

## 同梱簡易サーバーでの確認

1. 「mainをビルド」で現在の`main.cpp`から実行ファイルを作る。
2. 左端の「簡易サーバー」チェックを入れ、右側に表示される設定JSON、チーム、port、種別締切、開始待ちを確認する。
3. 「起動して使用」を押す。URL、TOKEN、workがローカル確認用へ切り替わる。
4. 「通信確認（手動）」を押す。
5. 「問題公開待ち・設定取得・種別選択・送信」を押し、対象日の「状態公開待ち・取得・探索」へ進む。日次回答の送信方法は画面上部で選ぶ。
6. 終了後に簡易サーバーの「停止」を押す。ウィンドウを閉じた場合も停止する。
7. 新しい試合を始める場合は、停止中に「実行設定・使用ファイル」の左に常時表示される「作業フォルダをクリア」を押して、前回の取得データ・回答・送信記録を削除する。

種別締切は起動時から進む。手動操作では余裕のある秒数にする。簡易サーバーは`127.0.0.1`だけで待ち受け、選択した設定内のTOKENを入力欄へ設定する。`.env`は書き換えない。
クリア対象は`runtime/simple-server/client/`の中身だけで、サーバーログと設定JSON原本は残る。実行前に確認ダイアログを表示し、簡易サーバーの実行中はボタンを無効化する。

## 試合操作

メイン画面の「実行設定・使用ファイル」から専用ウィンドウを開き、URLとTOKENを入力する。設定ウィンドウを閉じても入力値は保持される。通信確認後、メイン画面で次の順に操作する。

1. 「mainをビルド」を手動で押す。
2. 全工程を自動で進める場合は「試合終了まで全自動」を押す。問題公開待ち、種別選択・送信、各日の状態公開待ち、探索・回答送信を最終日まで繰り返す。「停止」で中断でき、再度押すと`automatic-progress.json`に保存した段階から再開する。

個別に操作する場合は次の手順を使う。

1. 「問題公開待ち・設定取得・種別選択・送信」を押す。問題公開前なら1秒間隔で待機し、公開後に設定取得、`agents.json`作成、種別のPOSTを順に実行する。待機は「停止」で中断できる。
2. 「状態公開待ち・取得・探索」を押す。対象dayが未公開なら1秒間隔で待機し、公開後に状態取得から`answer.json`と`score-next.json`の生成までを続けて実行する。「停止」で待機を中断できる。
3. 回答送信が「手動」なら確認して「日次回答を送信」を押す。「探索後に自動」なら探索成功後に確認ダイアログなしで送信する。
4. 初回取得後はボタンが「探索」に切り替わる。同じ日の再探索は取得済みの開始状態と当日の開始時チェックポイントを使用し、自動モードなら探索後に送信する。送信後も対象dayを維持し、日終了時刻を過ぎてから翌日に進む。次の日は2から繰り返す。

### 3人での本番運用

3台を有線LANへ接続し、別々の作業フォルダを使う。「実行設定・使用ファイル」で3台から見える同じLAN共有フォルダを指定してから、画面上部の「3人運用」で担当を選ぶ。Windowsでは共有元PCのフォルダを他の2台へネットワークドライブとして割り当てると扱いやすい。共有フォルダは試合ごとに新規作成または空にする。3人運用では共有フォルダが未設定・参照不能なら実行しない。

例として、共有元PCで`C:\ProconShare\match-01`を共有し、3台ともGUIの「共有フォルダ」にそのフォルダまたは割り当てた`Z:\match-01`を指定する。各PCでパス表記が異なっても、同じ共有内容が見えていればよい。TOKENや回答本文は共有せず、受理済みチェックポイントだけを置く。

ワークフローの1番ボタンは担当によって自動で切り替わる。通常・担当1では「1b 問題公開待ち・設定取得・種別選択・送信」、担当2・3では「1a 問題公開待ち・設定のみ取得（追走端末）」となる。担当1は「担当1：試合終了まで全自動」でエージェント種別の確定から最終日まで担当する。

| 担当 | 時間上限 | 実探索の目安 | 回答送信 |
|---|---:|---:|---|
| 担当1 先行 | 20,000 ms | 約15秒 | 問題公開待ちから最終日まで全自動 |
| 担当2 追走 | 40,000 ms | 約35秒 | 担当1より良い場合だけ手動送信 |
| 担当3 本命 | 60,000 ms | 約55秒 | それまでの最高より良い場合だけ手動送信 |

担当1は「担当1：試合終了まで全自動」を押すと、問題公開待ち、種別選択・送信、全日程の状態公開待ち・探索・回答送信を自動実行する。担当2・3は日次ボタンを使うため、全自動ボタンを無効化する。担当2・3は手動送信なので、探索中に通信timeout分を予約せず5秒の安全余裕だけを残し、表の約35秒／55秒を探索へ使う。時計左に表示される`系列数 / 総系列数 / 玉数`をこの順の公式辞書順で口頭比較し、改善した場合だけ「日次回答を送信」を押す。同点では第4基準の回答時刻が悪化するため送信しない。バックエンドも受理済み回答以下の候補をPOST前に拒否する。

画面上部の時計の左には、直近の探索後スコアを`系列数 / 総系列数 / 玉数`の順で常時表示する。これは公式比較の第1〜3基準で、担当間の口頭比較に使える。

当日の探索後、担当1は全自動のまま次日の状態公開を待つ。担当2・3は探索完了直後からバックグラウンドで待ち、`state-dayN.json`へ保存する。取得後はボタンが「探索」に変わる。次日探索に必要な、その日に最後に採用した回答の`score-dayN.json`は次段の共有処理で自動的に取り込む。

回答がHTTP 200で受理されると、送信端末はチェックポイントを共有フォルダへ保存する。ファイルは設定ハッシュ・次日・revisionを名前と内容に持つ不変ファイルで、複数端末の書き込み順が前後しても上書きしない。次日の状態取得直後、各端末は同じ設定・同じdayの最大revisionを選び、ローカルの`score-dayN.json`へ原子的にコピーしてから探索する。共有ファイルがない、設定が違う、共有フォルダを読めない場合は探索を開始しない。

日終了判定は状態の`endsAt`を優先し、未取得の日は設定の`startsAt`と`daySeconds`を使う。処理中は日付更新を保留し、最終日終了後は探索を無効化する。時刻不明の場合は対象dayを手動で変更する。

当日状態の取得成功時点で再探索用に記録するため、その後の探索が失敗しても「探索」から再試行できる。URL・TOKEN・作業フォルダ・設定パスを変更した場合は取得記録を破棄する。設定内容や保存状態が変わった場合も以前の状態を流用しない。この記録はGUI起動中だけ保持し、再起動後の初回は再取得する。

対象dayが翌日に変わっても、マップと探索結果は最後に取得・探索した日の表示を保つ。翌日の取得後に更新する。最終日終了時は対象dayが総日数と同じ値になり、「全日程終了」と表示して探索を無効化する。


dayは0始まりで、設定取得時に0へ戻り、入力範囲は`daySteps`の日数に合わせる。マップ上部では総日数を`days`、当日状態から取得する現在日を`day`として別々に表示するため、状態取得前は`day=未取得`でも`days`には設定済みの日数が表示される。さらに`steps`、`agents`、`spots`、`brands`、`fuelLimit`を表示する。`brands`はスポット設定に現れる系列IDの重複なし件数である。day 1以降の探索には、直前の回答が受理された後に確定した`score-dayN.json`が必要となる。手動の回答POSTの前には確認ダイアログを表示する。

設定を読み込むと、`startsAt`が確定している場合だけ試合開始予定を実行ログへ表示し、`daySeconds`を順に加算して「1日目終了予定」以降の全日程も表示する。開始時刻が0なら予定一覧を表示しない。

「日次回答の送信　手動　自動」と同じ行の一番右には、固定幅の状態1行と大きなタイマー1個だけを表示する。状態行は`0/8日 エージェント選択`、`3/8日 探索中`のように日程進捗と短い状態だけを示す。文言が変わっても時計領域の位置と幅は変えない。タイマーはエージェント選択、探索・送信処理、実際に進行中の各日の時間を表示する。問題公開待ち、当日状態公開待ち、試合開始待ちは`待機中`として`--:--:--`を表示し、フェーズ所要時間にも含めない。全日程終了後は終了からの経過時間へ切り替える。100ms周期で更新するが表示精度は秒単位。

実サーバーの設定JSONには種別受付終了の絶対時刻がないため、「エージェント選択」は試合開始までの残り時間を表示する。簡易サーバーでは起動時に得た選択終了時刻を使用し、その後に取得した`startsAt == 0`の設定で既知の開始時刻を消さない。開始時刻が未確定でも、当日状態の`endsAt`を取得後は現在日の残り時間を表示する。どちらも未取得の全自動処理中は、現在フェーズの経過時間へ切り替える。

簡易サーバー起動時は「種別締切(s)」と「開始待ち(s)」を基準に時刻を監視する。到達時に`⏰ 選択時間終了`、`⏰ 試合開始`を出力し、その後は設定JSONの`problem.daySeconds`に従って`⏰ 1日目終了`、`⏰ 2日目終了`のように出力する。簡易サーバーを停止または作業フォルダをクリアすると、未到達の通知を取り消す。

全自動実行は次の日の状態が公開されるまで待機する。送信失敗時は自動再送せず、結果不明の送信記録を保護する。設定読込時と対象day変更時に、当日の`daySeconds`を探索時間上限の初期値としてミリ秒単位で表示し、実行前に短い値へ変更できる。日次探索時間は設定の`daySeconds`未満へも自動制限し、送信確保時間・時刻余裕は探索パラメータ画面で指定する。別試合は新しい作業フォルダを使う。送信しないローカル設定の探索は「実行設定・使用ファイル」から実行できる。

「実行設定・使用ファイル」のランダム設定では、幅、高さ、エージェント数、スポット数、系列数、日数、1日の秒数、チーム数を指定できる。seed入力欄は置かず、毎回新しいseedで生成する。生成を許可する組合せは[`sample_maps/README.md`](../../sample_maps/README.md)の3区分のみで、行動回答時間は60秒に固定する。初期値は32×32、7エージェント、32スポット、28系列、10日である。「ランダム生成して探索」はC++の`ProblemCreator`で`work/random-setting.json`を生成し、そのファイルを選択状態にして「ローカル設定を探索」と同じ処理を自動的に開始する。生成時のseedはログから確認でき、CLIでは同じseedを指定して再現できる。

## 表示と安全性

- マップタブは地形、混雑・渋滞を表示し、右側の状態表にエージェントの種別（P/S）、`pos(x,y)`形式の位置、燃料、現在/上限ステップとスポットの系列、残数/初期数形式の在庫を表示する。ローカル設定の探索完了後は`result-state.json`を読み込み、状態表とマップ上のエージェントを探索後状態へ更新する。
- 探索完了後は各車の移動経路を別の色で表示する。線、マップ上の個体、一覧は同じ色を使い、次の探索開始時に線を消す。
- ワークフロー直下の探索結果枠には、対象day、終了理由、探索時間、展開ノード数、その日の総獲得数、全日程の合計獲得数、当日と全日程の獲得系列数を表示する。公式比較値は重複表示せず、時計左の`系列数 / 総系列数 / 玉数`へまとめる。当日分は設定時点の単日上限、全日程分は各日の理論上限を合算した値を分母にする。全日程の系列実績は各日の取得系列数の累計で、試合全体の重複なし系列数とは別の値である。ローカル探索と日次探索の両方を更新する。
- ワークフローと探索パラメータは固定パネルにまとめ、通常の画面サイズではスクロールなしで操作できる。
- マップは表示領域へ自動的に縮小・中央配置し、収まる場合はスクロールバーを隠す。
- 実行ログは画面最下部へ横幅いっぱいに表示する。
- ワークフローは左側の300px以上を目安とする操作パネルにまとめ、探索結果の長い項目名も読みやすい幅を確保する。実際の幅はウィンドウサイズとペイン配置に応じて変わる。
- 実行設定と使用ファイルは専用ウィンドウに分離し、メイン画面右上のボタンで開く。
- JSONと実行ログのスクロールバーも、内容が表示領域を超えた場合だけ表示する。
- JSONタブは設定、状態、種別、回答、次日得点を表示する。単純な配列とオブジェクトは1行にまとめ、経路などの入れ子配列は配列単位で改行する。
- 探索パラメータは実行開始時に[`solver_options.hpp`](../inc/solver_options.md)用CLI引数へ変換する。
- HTTPとソルバーはバックグラウンドで実行し、Tk部品の更新だけをメインスレッドで行う。
- TOKENは接続内容を確認できるよう入力欄へ通常表示する。画面共有時の映り込みに注意する。GUIログへ現れた同じ文字列は引き続き置換する。

ファイル選択ダイアログは`_choose_file()`に集約し、選択値の反映、JSON表示、選択後の再読込処理を引数で指定する。設定、状態、得点、ソルバー、`.env`、簡易サーバー設定の各ボタンはこの共通処理を使用する。マップ描画ではセル番号から中心座標を求める`cell_center()`をセル本体と回答経路の両方で使用し、六角形と経路線の座標計算を一致させる。

画面が空白になる場合は[`runtime.py`](runtime.md)の実行環境確認を行う。

ランダム設定の「道路状態（ローカル探索）」で「混雑・渋滞を含める」を選べる。オフなら全道路が順調、オンなら順調・混雑・渋滞から各道路へランダムに割り当てる。その回の生成seedを道路状態にも使うため、GUIで再生成すると地形と交通の両方が新しくなる。

道路状態は生成設定のローカル用追加項目`localTraffics`へ保存し、GUIのローカル探索では`local-state.json`としてソルバーへ渡す。初期表示・探索後表示にも同じ状態を使う。これはローカル検証用の交通条件で、実サーバーから取得した当日状態は変更しない。C++ CLIから設定ファイルだけを直接探索する場合は追加項目を使用しない。
