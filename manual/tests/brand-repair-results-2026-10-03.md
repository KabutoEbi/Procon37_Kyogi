# 系列救済型の連鎖再計画（2026-10-03）

`newAlgo`ブランチに、ビームの未獲得系列を対象とした連鎖再計画を追加した。巻き戻した状態から巡回車1〜2台と補給車1台を自由にし、他の車の行動は固定する。全車の公式シミュレーションで系列数が厳密に改善した計画だけを採用する。

## 比較条件

- Apple clang 21.0.0、arm64、C++17、`-O2 -pthread`、1スレッド。
- 既存方式: ビーム＋全車の系列補完。新方式: 同じビーム＋連鎖再計画＋全車の系列補完。巡回先の共同割当、迂回補給、2店先読みなどは両方式で有効。
- 時間制限付き比較は両方とも1日300ms、安全余裕0ms。ビームへ80%を確保する点は同じ。新方式はビーム終了後の残時間の75%を連鎖再計画へ、残りを全車探索へ配分する。
- 連鎖再計画は最大16試行、各1000状態。全車の補完は最大10000状態。全体の締切と各試行の締切を守る。
- 生成問題は8/16/24/32の4サイズ。8/16は4台、24/32は8台で、いずれも最後の1台を補給車に固定。スポット数は盤面サイズ、系列数はその3/4。
- 各ペアの実行順はseed・反復ごとに交替する。ベンチマーク中はビルド・テスト・他のベンチマークを同時に実行しない。
- 全計画を前日得点込みで再生し、終了状態一致・フォールバック未使用を確認する。

## 同じ時間上限での結果

得点は各試合の最終日の値を合計する。初日だけの比較では試合系列と日別系列が一致する。

| 条件 | ペア数 | 指標 | 既存 | 連鎖再計画 |
|---|---:|---|---:|---:|
| 初日、混合交通、seed 1〜8、3反復、4サイズ | 96 | 試合系列 / 日別系列 / 玉数 | 1434 / 1434 / 5209 | 1437 / 1437 / 5216 |
| 4日、混合交通、燃料上限＝初日ステップ数の半分、seed 1〜4、2反復、4サイズ | 32 | 試合系列 / 日別系列 / 玉数 | 480 / 1695 / 3289 | 480 / 1801 / 3535 |
| 4日、混合交通、通常燃料、別シード21〜24、2反復、4サイズ | 32 | 試合系列 / 日別系列 / 玉数 | 480 / 1881 / 6033 | 480 / 1917 / 5986 |

辞書順の試合得点での勝ち／同点／負けは、初日比較が`7 / 87 / 2`、厳しい燃料の4日間が`18 / 11 / 3`、通常燃料の別シードが`11 / 12 / 9`だった。新方式の日次最大経過時間はいずれも300ms（ミリ秒単位に切り捨てた値）。

初日比較の16×16・seed 4は、3反復すべてで`11系列→12系列`、玉数は13のまま。局所補完の採用を各反復で確認した。8/24/32の初日比較では局所補完の採用は0件であり、これらの玉数差は局所再計画の改善として数えない。時間打切りでビームの探索量・終了位置が変動するため、得点差が出る場合がある。

厳しい燃料の4日間では日別系列累計が106、玉数が246増えた。サイズ別の日別系列累計は、8が`192→192`、16が`366→376`、24が`535→565`、32が`602→668`。局所補完は計41回採用した。ただし32×32・seed 1の2反復では試合終了時の日別系列累計が下がり、もう1組は系列同数で玉数が下がった。試合全体の非退行は確認できていない。

通常燃料の別シードでは日別系列累計が36増え、玉数は47減った。日別系列累計は16が`383→384`、24が`538→573`、8/32は同数。局所補完は計15回採用した。9組の負けはいずれも系列数は同じで、玉数の差によるものだった。

系列数を優先する目的では改善を確認したため既定で有効にした。全試合で得点が改善することや全体最適性は保証しない。従来方式は`--brand-repair 0`、最適性の証明を目的とする全車探索は`--exact-brands 1`で実行できる。

## 固定幅での取りこぼし確認

16×16・seed 1〜8、初日のみ、混合交通、ビーム幅32／同時行動幅128、締切なしの比較では、系列数合計が`94→95`、玉数合計は204で同じ、勝ち／同点／負けは`2 / 6 / 0`だった。両方式の主ビーム展開数は758447で一致し、主ビームの探索量の差を除いて取りこぼし補完を確認した。

seed 4は`11系列 / 14玉→12系列 / 12玉`、seed 8は系列数11のまま`11玉→13玉`。seed 8の局所採用数は1だが、全車探索前のビーム計画に対する系列改善であり、既存の全車探索より系列数が増えたことは意味しない。

この比較は局所探索の追加計算量が異なるため、同じ総探索量・同じ時間の比較ではない。探索時間の中央値／最大値は既存が54／77ms、新方式が50／108ms。時間性能の評価には上の300ms制限比較を使用する。

別シード21〜24、4日間、4サイズ、同じ固定幅、各1反復の16ペアでも比較した。得点合計は既存`240 / 951 / 2931`、新方式`240 / 959 / 2894`、勝ち／同点／負けは`1 / 14 / 1`。64日ペア中59日で行動列のハッシュが完全一致した。

24×24・seed 23は日別系列累計`64→72`、玉数`182→146`。32×32・seed 23は系列数が同じで玉数`291→290`となった。他14ペアの試合得点は完全一致した。これにより、時間打切りの揺れを除いても系列救済による改善と玉数の減少があることを確認した。試合時間の中央値／最大値は既存432／37144ms、新方式449／1207ms。締切なしの比較であり、本番の回答時間として解釈しない。

## 回帰検証

- `make -j3 test`: C++8テスト、サンプル16/24/32、Python35件と実ソルバー4日間連携を通過。
- `make -j3 test-sanitize`: サンプル以外のC++7テストをASan/UBSanで通過。
- 新規テストでは、Aだけの再計画では系列が増えず、Bの役割交換で増える例、補給が必要な役割交換、固定車の行動維持、待機途中での巻き戻し、予約中の移動維持を検証。
- 混合交通16シードで新計画の合法性、終了状態一致、当日系列数の非退行、試行数・展開上限を検証。
- 既存の系列最大化と独立した全計画列挙48ケースの照合も通過。
- 5条件の比較CSVの計848日分すべてで`valid=1`を確認した。

## 再現

```sh
make .build/tools/solver_benchmark

.build/tools/solver_benchmark --compare-brand-repair \
  --size 16 --seeds 8 --repeats 1 --single-day --fixed-work --mixed-traffic \
  > .build/brand-repair-fixed-16.csv

.build/tools/solver_benchmark --compare-brand-repair \
  --seeds 8 --repeats 3 --single-day --mixed-traffic --time-ms 300 \
  > .build/brand-repair-timed-single.csv

.build/tools/solver_benchmark --compare-brand-repair \
  --seeds 4 --repeats 2 --days 4 --mixed-traffic --tight-fuel --time-ms 300 \
  > .build/brand-repair-timed-tight-multiday.csv

.build/tools/solver_benchmark --compare-brand-repair \
  --seed-start 21 --seeds 4 --repeats 2 --days 4 --mixed-traffic --time-ms 300 \
  > .build/brand-repair-timed-normal-holdout.csv

.build/tools/solver_benchmark --compare-brand-repair \
  --seed-start 21 --seeds 4 --repeats 1 --days 4 --mixed-traffic --fixed-work \
  > .build/brand-repair-fixed-holdout.csv
```

CSVの`repair_attempts / repair_expanded / repair_improvements`は、局所補完の試行数・状態展開数・採用数。`repair_improvements`はビームに対する改善数であり、既存補完方式より勝った件数とは区別する。実時間制限での数値はCPU負荷や打切り位置によって変動する。
