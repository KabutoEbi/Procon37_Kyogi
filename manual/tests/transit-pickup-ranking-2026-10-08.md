# 通過取得を反映した玉数候補順位の検証（2026-10-08）

## 変更

巡回車別の経路候補ラベルを伸ばす際、明示的な目的店だけでなく、復元した最短経路上で通過する全店舗を取得スポット・系列・玉数へ加える。完成候補は従来どおり公式シミュレータで再生し、合法性、在庫、補給時刻、得点を確認する。

従来も完成経路の通過取得自体はシミュレータで計上していたが、幅24へ絞る前のラベル順位は目的店だけを数えていた。そのため、実際には複数玉を取る経路が候補プールへ到達する前に落ちる場合があった。

## 適用範囲

`RouteColumnConfig::rankTransitPickups`の既定値はtrue。ただし実測結果から32×32だけに適用し、16×16・24×24は従来順位を維持する。比較用ベンチマークは`--variant no-transit-pickup-ranking`。

## 比較

すべて混合交通で、数値は試合系列／日別系列／玉数。

| 条件 | 通過取得順位ON | OFF |
|---|---:|---:|
| 32×32、7台、24系列、単日、4シード×2反復、5秒 | 192 / 192 / 734 | 192 / 192 / 712 |
| 同条件、末尾待機探索OFF、4シード×1反復、5秒 | 96 / 96 / 365 | 96 / 96 / 356 |
| 32×32、7台、24系列、単日、4シード、10秒 | 96 / 96 / 377 | 96 / 96 / 369 |
| 32×32、7台、24系列、4日、seed 31〜33、3秒 | 72 / 288 / 1071 | 72 / 288 / 1071 |
| 24×24、5台、16系列、4日、seed 21〜23、3秒 | 48 / 191 / 516 | 48 / 191 / 517 |

32×32の単日条件では系列数を維持して5秒で22玉、10秒で8玉増加した。4日条件は同点。24×24では1玉下がったため適用対象から外した。時間打切りの少数シード比較であり、全盤面の非退行は保証しない。

`make -j4 test-core`でC++回帰、Python 39件、通常ビルドが成功した。`make -j4 test-sanitize`でC++ 10テストをASan/UBSan実行し、異常なし。最終バイナリは`-O3 -DNDEBUG -Wall -Wextra -Wpedantic -Werror`で再ビルドした。

## 棄却した同時検討案

- 補給スケジュールの既存案へ30%の固定予算を与える方式は、32×32・5秒で`712対716`となったため撤回。
- 経路組合せを候補数の少ない巡回車から解く方式は`712対714`となったため撤回。
- 玉数ALNSの同時解放車を取得担当交換の距離差で選ぶ方式は、24×24・4日で`516対517`となったため撤回。
- 末尾待機活用を既存局所探索より先に実行すると32×32・5秒で`714対716`となった。後段へ移しても複数車LNSの時間を消費し得るため、機能と単体テストは残すが既定falseとした。
- 32×32・5秒で経路ラベル幅を24から32、48へ広げる案は、同一4シードで基準360玉に対して358玉、357玉だった。巡回車ごとの最終候補数を32から48へ広げる案も359玉で、いずれも後段探索の時間を圧迫したため撤回。
- ラベル幅の半分を経過時間優先から取得数優先へ変える案は357玉だった。早い途中状態を残せず、後続店舗へ伸ばす余地を失うため撤回。
- 固定待機案を2件から1件へ、または時刻付き合流を最大3回から2回へ個別に減らした条件は、どちらも現行相当の360玉で同点だった。後者は補給量が1202から1151へ下がり、最終補給後の待機も54から139へ増えたため、得点同点でも現設定を維持した。
- 巡回車ごとの32経路候補について、単独玉数枠を約21本から16本へ減らし、他車との在庫競合回避枠を約6本から8本へ増やす案は360玉で完全同点だった。候補プールの最終解を変えなかったため撤回。
- 経路探索と玉数ALNSの時間配分は、経路側60%で362玉、67%で365玉、既定75%で367玉、80%で367玉、85%で366玉だった。ALNSを無効化した100%相当は8試行で723玉、既定は732玉だったため75%を維持した。
- 経路組合せ探索の上限を15万から30万ノードへ増やす案は365玉で、既定15万の367玉を下回った。seed 3では約24.8万ノードまで探索できたが、後段へ渡す時間が減ったため撤回。
