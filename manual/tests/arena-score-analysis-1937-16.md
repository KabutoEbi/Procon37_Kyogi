# 公開試合1937までの16×16目標と改善（2026-10-10）

取得元: [試合一覧API](https://procon37arena.online/api/matches)、
詳細`GET /api/matches/{id}`。今回一覧を再取得し、#1932～#1937の6詳細を追加取得した。
過去の詳細キャッシュと合わせ、16×16・4台・`scored`・`verified`の67試合を
36独立ラウンドへ統合した。同一ラウンドの最大**公式得点順**
（系列→日別系列→玉数）を目標とし、玉数だけが多い系列不足の結果は選ばない。
問題JSONと取得キャッシュは一時領域に保存し、リポジトリに同梱しない。

36/36ラウンドで上位は系列・日別系列が満点。したがって玉数だけを増やすために
系列を落とす変更は採用しない。上位玉数の中央値は159だが、日数・ステップ・
在庫が異なるため、この値を全問題共通の目標にはしない。

## 採用: 最終日の追加経路組合せ

通常のビーム、系列修復、経路組合せ、SAを先に実行し、最後に残時間がある場合だけ
16×16の最終日を追加改善する。ラベル幅24→48、車別候補32→48、
組合せ展開上限150,000→250,000の独立候補を、完成済み計画を起点に比較する。
公式再生と公式得点順で改善した場合だけ採用する。

- 中間日は一切変更しない。翌日の配置・燃料を動かさない。
- 両系列上限達成後に限る。通常探索の予算予約・締切を変更しない。
- 1日の予算5秒以上で既存の経路候補探索が有効な場合に限る。
- `smallBoardFinalColumns=true`が既定、CLIの`--small-board-final-columns 0`で無効化。
- 24×24以上、長方形、系列不足時には適用しない。

## 検証

5秒/日・幅256/1024・初日順調／以後mixedの時間制限比較は、
1936が双方`14/55/79`、1935が双方`10/40/97`（0勝2分0敗）。
全日5秒以内に終了した。系列不足時は追加玉数探索をせず、通常の系列救済を維持する。
本番の自動幅・15/35/45秒運用とは異なる短時間測定であり、目標達成の証明ではない。

```sh
python3 tests/small_board_api_benchmark.py --time-ms 5000 --beam-width 256 \
  /tmp/procon37-1936.json /tmp/procon37-1935.json
```

`make -j2 test-core`が成功。C++の最終日だけの適用・中間日の計画不変・
長方形で無効・公式再生一致・CLI拒否値の回帰と、Python 66件が成功した。
API集計はラウンド重複排除、系列優先、未検証結果の除外を4件のテストで検査する。
`make test-samples`も公開16×16・24×24・32×32で成功した。
`main`は`-O3 -DNDEBUG -Wall -Wextra -Wpedantic -Werror`で最適化再ビルドした。

## 不採用の案

- 短い翌日が連続する16×16で遠隔一意系列への準備を強める案:
  最新4問題は1勝3分だったが、別6問題で1勝4分1敗。
  #1853の玉数144→142で退行したため撤回。
- すべての日の通常経路候補を広い候補へ置換する案:
  #1936が`14/56/80→14/54/85`となり、玉数増加より重大な日別系列不足が発生。
- 通常経路候補の後に終点固定の広い候補を追加する案:
  #1935で101→97玉。残燃料やSA初期スコアの変化は翌日以降の退行を防げなかった。
  このため、採用方式は最終日の**通常SA完了後**に限った。

`mixed`は従来どおり初日も混雑させるストレス試験として維持し、
今回の公式初期条件に合わせた比較は新しい`mixed-after-first`を使う。
初日混雑の探索用単発測定や、回帰試験と並行した実時間測定は採用根拠にしない。
