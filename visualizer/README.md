# ビジュアライザ

回答システムからの取得、エージェント種別選択、日次探索、送信を操作するTkアプリである。各段階を手動で操作できるほか、「試合終了まで全自動」で問題公開待ちから全日程の回答送信まで続けて実行できる。公式JSONのマップ、交通状態、自チームの位置・燃料、生成JSON、実行ログも確認できる。

アプリアイコンは白背景に黒線のベンゼン環を使用する。ベクター原稿は`assets/app_icon.svg`、Tkで表示する画像は`assets/app_icon.png`である。

## 起動

リポジトリ直下で実行する。

```sh
python3 visualizer/app.py
```

Python 3.9以降とTkを使用する。`tkinter`がない場合は、使用するPythonに対応するTkパッケージを追加する。新しい探索オプションを使用するため、最初にGUIの「mainを最適化ビルド」で`-O3 -DNDEBUG`の本番向け実行ファイルを更新する。

macOSではTk 8.6以降を使用する。`python3`が古いシステムTk 8.5を使っている場合は、起動時にインストール済みのHomebrew版／python.org版Pythonを探し、対応するTkを持つPythonへ自動的に切り替える。新たなパッケージのインストールは行わない。

ウィンドウ全体が空白になる場合は、古いウィンドウを閉じて上記コマンドで再起動する。次のコマンドなら、画面を開かずに切り替え後の実行環境を確認できる。

```sh
python3 visualizer/app.py --check-runtime
```

対応するPythonがない場合は、空白のウィンドウを作らずターミナルに理由を表示する。Apple提供の古いTkについては[Python公式のmacOS向け説明](https://www.python.org/download/mac/tcltk/)も参照。

## 同梱の簡易サーバーで確認

実サーバーへ接続しなくても、画面上部の左端にある「簡易サーバー」チェックから取得・探索・送信を一通り確認できる。チェックを入れると右側に設定が表示され、本番利用時は未チェックのまま隠しておける。

1. 先に「mainを最適化ビルド」を押す。簡易サーバー起動後は種別締切までの時間が進むため、ビルドを先に済ませる。
2. 通常は設定JSON、チーム、port、時間を初期値のままにする。
3. 「起動して使用」を押す。OS/CPUに合う同梱バイナリを選び、`127.0.0.1`だけで待ち受ける。
4. URL、TOKEN、作業フォルダが簡易サーバー用に自動で切り替わったことを確認する。
5. 「問題公開待ち・設定取得・種別選択・送信」を押し、続いて対象日の「状態公開待ち・取得・探索」を押す。回答送信を自動にする場合は画面上部で切り替える。
6. 終了後に「停止」を押す。GUIを閉じた場合も同梱サーバーは停止する。
7. 同じ保存先で新しい試合を始める場合は、停止中に「実行設定・使用ファイル」の左に常時表示される「作業フォルダをクリア」を押す。確認後、クライアント側の取得物・回答・送信記録だけを削除する。

初期設定は`回答システムに関する情報・簡易版の回答用サーバー/試合設定用JSONファイル/example.json`、チームは`team-0`、URLは`http://127.0.0.1:8080`である。種別締切は簡易サーバー起動時から進む。手動確認で間に合わない場合は起動前に「種別締切(s)」を増やす。起動後の時間設定は変更できないため、停止して起動し直す。

簡易サーバー本体の出力は`runtime/simple-server/simple-server.log`、クライアント側の取得物・回答・通信ログは`runtime/simple-server/client/`へ分離して保存する。入力した実サーバー用TOKENや`.env`は変更しない。
「作業フォルダをクリア」は`client/`の中身だけを対象にし、サーバーログと設定JSON原本は残す。送信結果不明の記録も削除されて復旧できなくなるため、別試合または再試合を開始するときに使用する。

## 操作手順

1. メイン画面の「実行設定・使用ファイル」から専用ウィンドウを開き、URLとTOKEN入力欄を設定する。`.env`の値を初期表示するが、直接入力した値がその実行で使われる。TOKENは通常表示するため、画面共有時は注意する。入力値は`.env`へ自動保存しない。
   接続テスト・予行演習・第1試合・準決勝・決勝はすべて同じ`.env`の本番URL/TOKENを使用する。簡易サーバーは別途明示的にチェックした場合だけ使用する。
2. 試合区分を「予行演習」「第1試合」「準決勝」「決勝」のいずれかへ切り替え、担当を選んでから「mainを最適化ビルド」を手動で押す。ボタンに現在の試合区分と担当が表示され、押下時に両方の実行設定を再適用する。共有フォルダの設定は不要である。主催者が指定した接続テスト時間中は試合区分を「接続テスト」にして「接続テスト（全日ダミー送信）」を押す。
3. 全工程を任せる場合は「試合終了まで全自動」を押す。問題・各日の公開を待ちながら、種別選択、探索、送信を最終日まで繰り返す。「停止」で中断でき、同じボタンで保存済みの段階から再開できる。

個別に確認しながら進める場合は、次の手動操作を使う。

1. 「問題公開待ち・設定取得・種別選択・送信」を押す。公開前は1秒間隔で待機し、公開後に`GET /setting`、`agents.json`の生成、`POST /agent`を順に実行する。
2. 対象dayを指定して「状態公開待ち・取得・探索」を押す。未公開中は1秒間隔で待機し、公開後に`answer.json`と`score-next.json`を作る。「停止」で中断できる。
3. 回答送信が「手動」なら内容を確認して「日次回答を送信」を押す。「探索後に自動」なら探索成功後に確認ダイアログなしで送信する。
4. 初回取得後はボタンが「探索」に切り替わり、その日の開始状態で再探索できる。自動モードなら再探索後も送信する。送信後も対象dayは維持し、日終了時刻を過ぎてから翌日に更新する。翌日の初回は再び「状態公開待ち・取得・探索」を押す。

「試合終了まで全自動」と通常担当の個別操作は、エージェント種別を3段階で扱う。軽量な初期構成を即時送信し、選択探索時間の中間点と受付終了10秒前に、直前の受理済み構成を厳密に上回る候補だけを送信する。探索時間は第1試合50秒、準決勝80秒、決勝110秒である。「試合終了まで全自動」と「探索後に自動」は日次回答も3段階で扱う。最短路ベースの貪欲解を即時送信し、ビーム幅を広げても公式得点が変わらない、またはSA近傍で改善が止まった時点に提出済みベストより良ければ中間送信する。さらに公式回答枠の終了10秒前まで探索し、その時点の候補が提出済みベストを厳密に上回れば最終送信する。同点以下では再送しない。

画面上部の「試合区分」は実サーバーへの接続先を変えず、処理内容と回答時間を切り替える。「接続テスト」だけがダミー送信専用である。「予行演習」はエージェント回答・行動回答とも30秒。「第1試合」は16×16で両方60秒。「準決勝」は24×24でエージェント選択90秒・行動回答60秒。「決勝」は32×32でエージェント選択120秒・行動回答60秒である。実ソルバーによる種別選択・日次探索と、生成回答の実サーバーへの送信を最終日まで行う。取得した設定の`daySeconds`は日次探索へ自動反映される。

接続テストは試合前10秒、エージェント選択カウントダウン10秒、エージェントタイプ回答20秒、行動回答20秒×4日である。問題と各日の状態は実サーバーから取得し、送信データだけをダミーにする。開始時に`GET /setting`を行い、公開前の403は最大25秒待機する。取得設定が20秒×4日であることを確認してから、`[0,1,0,1,...]`のダミー種別を`POST /agent`へ送る。その後は各日の状態を`GET /`で取得し、全エージェントについて全ステップ待機する`[[-daySteps[day]], ...]`だけを`POST /`へ送る。全4日のHTTP 200と0以上のrevisionを確認できた場合だけ成功と表示する。ダミー送信は「接続テスト」区分でしか実行できず、他の試合区分では拒否する。

予行演習では試合区分を「予行演習」に切り替えてから「試合終了まで全自動」を実行する。取得後の表示が16×16、5日、32/36/40/40/48ステップ、4台、16スポット、10系列、在庫合計30、燃料40、混雑1、渋滞2であることを確認し、不一致警告が出た場合は送信前に中止する。

準決勝・決勝は「3人運用」を「通常」にして1人・1端末で実行する。準決勝では試合区分を「準決勝」にし、24×24、6日、日別ステップ`48,56,68,68,56,72`、5台、24スポット、18系列、最大在庫合計60、燃料80、混雑1、渋滞2、各日の回答60秒であることを確認する。決勝では「決勝」にして、32×32、7台、32スポット、20〜28系列、各日の回答60秒であることを確認する。不一致警告が出た場合は送信前に選択区分と取得設定を見直す。

### 3人で探索して口頭比較する本番運用

3台は別々の作業フォルダを使用し、画面上部の「3人運用」から担当を選ぶ。有線LANや共有フォルダは使用しない。
選択するとビーム幅が自動選択になり、担当1・2は`--udon-sa 0`のビーム系探索、担当3は`--udon-sa 1`の焼きなましになる。探索時間上限は安全余裕5秒を含めて次の値になる。

| 担当 | 設定値 | 探索目安 | 操作 |
|---|---:|---:|---|
| 担当1 停滞検出ビーム | 試合区分の回答時間 | 締切10秒前まで（停滞時は早期終了） | 問題公開待ちから最終日まで全自動 |
| 担当2 収束ビーム | 予行20,000 / 本番40,000 ms | 約15秒 / 約35秒 | 結果が安定したら幅拡大を止め、系列上限未達なら系列救済後に終了。担当1より公式スコアが高い場合だけ送信 |
| 担当3 収束SA | 予行20,000 / 本番50,000 ms | 約15秒 / 約45秒 | 最良解の更新が止まったら終了し、それまでの最高値より高い場合だけ送信 |

ビルド成果物は3担当と全試合区分で共通の`-O3 -DNDEBUG`の`main`で、探索方式と時間はGUIが実行時引数として固定する。起動時は第1試合を初期選択する。ビルドボタンには選択中の試合区分と担当プロファイルを表示し、ビルド時にその組合せを再適用する。

1番ボタンは担当に応じて切り替わる。通常・担当1は「1b 問題公開待ち・設定取得・種別選択・送信」、担当2・3は「1a 問題公開待ち・設定のみ取得（追走端末）」となり、追走端末はエージェント種別を上書きしない。担当1は「担当1：試合終了まで全自動」を使用し、問題公開待ちから最終日まで自動実行する。
1日目以降、担当2・3は各端末で「2 状態公開待ち・取得・探索」を実行する。
担当2・3は時計の左にある`系列数 / 総系列数 / 玉数`を左から辞書順に比較する。
勝っている端末だけが「3 日次回答を送信」を押す。同点は送信しない。

探索が終了すると、画面上部の入力欄の上に`系列mask 玉数 日別系列累計`の3整数が自動表示される。この領域は「停止」の右隣にあり、上段が候補比較と読み上げに使う3値、下段が受信用の入力欄と「取込」である。3台で候補を比較し、採用する回答がHTTP 200で受理された後、その端末の上段3値だけを引き継ぐ。他の2人はこれから探索する対象日を選び、下段へ空白区切りで1行入力してEnterを押す。マウス操作なら「取込」を押す。`nextDay`は対象日から自動生成される。保存に成功すると入力欄は空になり、形式や対象dayのエラー時は修正できるよう値を残す。最終日の回答後は次日がないため、取込不要と案内してファイルを作らない。未送信・未受理候補の3値は取り込まない。口頭方式は試合・TOKEN・revisionを自動照合しないため、受信側は対象日と3値を必ず復唱する。

担当1は全自動フローのまま次日の状態公開を待つ。担当2・3は当日探索が終わるとバックグラウンドで次日の状態公開を待ち、`state-dayN.json`へ自動保存する。次日の探索前までに、その日の最後に受理された回答の3値を各端末へ取り込む。より良い回答が同日に再受理された場合は、新しい3値でもう一度取り込む。

全自動は担当1だけで有効にし、担当2・3では誤送信防止のため無効化する。
「3人運用」が「通常」のときも従来どおり全自動を利用できる。
入力順、日番号との対応、復唱方法は[口頭による次日チェックポイント共有](../manual/spoken_checkpoint_sharing.md)を参照する。

日終了判定は取得状態の`endsAt`を優先し、未取得の日は設定の`startsAt`と`daySeconds`を使う。処理中は対象日を変更せず、処理後に更新する。最終日終了後は探索ボタンを無効化する。時刻不明の場合は対象dayを手動で変更する。初回取得に成功して探索だけが失敗した場合も、再取得せず再探索できる。

GUI上のdayは1始まり。API・JSON・`state-dayN.json`などのファイル名は仕様どおり0始まりのまま扱う。設定取得時に対象dayを1へ戻し、入力範囲を1〜設定日数に合わせる。マップ上部の`days`は設定の`daySteps`から得た総日数、`day`は当日状態から得た現在日を1始まりで表示し、状態取得前の`day`は「未取得」と表示する。同じ欄にエージェント数、スポット数、系列数、燃料上限も表示する。問題取得時はスポット・初期配置を、種別選択後はP/Sを、各日取得時は交通と現在位置・燃料を表示する。問題を切り替えると前の状態表示をクリアする。
設定読込時には、`startsAt`が確定していれば`daySeconds`から試合開始と各日終了の予定日時を計算し、実行ログへ表示する。開始時刻が未確定の設定では予定一覧を表示しない。同じ設定の再表示では日程を重複出力しない。簡易サーバーでは起動時の「種別締切(s)」も監視し、時刻に達した瞬間に`⏰ 選択時間終了`を出力する。試合開始と各日終了も同様に、予定一覧とは別の確定メッセージを出力する。

「日次回答の送信　手動　自動」と同じ行の一番右には、固定幅の状態1行とタイマー1個だけをコンパクトに表示する。状態は`0/8日 エージェント選択`、`3/8日 探索中`のように日程進捗と短い処理名だけを示し、文言が変わっても時計の位置を動かさない。タイマーは、エージェント選択、探索・送信処理、実際に進行中の各日の時間を`分:秒`で表示する。60分以上は分を繰り上げ、61分1秒は`61:01`とする。問題公開待ち、当日状態公開待ち、試合開始待ちは`待機中`として`--:--`を表示し、時間を計らない。簡易サーバーでは設定した種別締切を使い、後から取得した`startsAt == 0`で既知の開始時刻を消さない。開始時刻が不明でも当日状態の`endsAt`があれば現在日の残り時間を表示する。時刻はPCの時計を基準に100ms周期で更新する。

時計の左には、直近探索の公式第1〜3基準を`系列数 / 総系列数 / 玉数`として大きく表示する。新しい探索結果が出ると更新する。
探索完了時は当日の各エージェントの移動経路をマップに異なる色の線で表示する。線、マップ上のエージェント、エージェント一覧は同じ色を使う。待機は線に含めず、次の日の探索開始時に線を消す。エージェント一覧は種別をP/S、位置を`pos(x,y)`、ステップを現在値/当日上限で表示する。スポット一覧の在庫は残数/初期数で表示する。ローカル探索、手動日次探索、全自動探索の完了後は、経路の始点には当日開始状態を使い、エージェント位置・燃料・ステップとスポット残在庫は`result-state.json`の探索後状態を表示する。
左側のワークフロー直下に探索結果を表示する。対象day、終了理由、探索時間、展開ノード数、その日の総獲得数、全日程の合計獲得数、当日と全日程の獲得系列数を、ローカル探索と日次探索の完了時に更新する。探索中、停止、失敗も同じ枠の状態欄へ表示する。

手動送信では確認ダイアログが表示される。日次回答が受理された後だけ、予測得点`score-next.json`を`score-dayN.json`として次日に引き継ぐ。送信する回答・接続先・当日状態は探索時の記録と照合する。停止／失敗した探索の旧回答やローカル探索の回答は、GUIの日次送信には使用しない。送信失敗時は自動再送せず、結果不明の送信記録を保護する。

「停止」で実行中の処理を停止する。探索プロセスは終了し、再開時はその探索をやり直す。実行中のHTTPは応答またはタイムアウトを待つ。別試合・再試合では新しい作業フォルダを使用し、同じフォルダをGUIとCLIから同時に操作しない。

## 探索パラメータ

「探索パラメータ」タブで変更する。値は実行開始時に固定し、`main`のCLIオプションへ渡す。

| 設定 | GUI初期値 | 備考 |
|---|---:|---|
| ビーム幅 / 同時行動幅 | 128 / 512 | 1以上 |
| スレッド数 | 0 | 0: 自動、1: 直列 |
| 探索時間上限 | 対象日の`daySeconds` | 設定読込・day変更時にms単位で反映。短い値へ変更可能 |
| 締切余裕 | 5000 ms | 探索・種別選択の締切から差し引く |
| 各車の行動候補数 | 4 | 0: 全候補 |
| マクロ行動 / ビーム幅自動調整 | 1 / 1 | 1: 有効、0: 無効 |
| 種別選択の試走候補数 | 0 | 全自動では受付優先。必要なら手動で増加 |
| 種別選択の試走幅 / 同時行動幅 | 32 / 128 | 1以上 |
| 種別選択時間上限 | 予行30,000 / 第1試合60,000 / 準決勝90,000 / 決勝120,000 ms | 画面上部の「試合区分」で切替 |
| 送信確保時間 | 5000 ms | timeout＋時刻余裕＋保存・レート制限用1200ms以上を自動確保 |
| 時刻余裕 | 1000 ms | OSとサーバーの時刻差用。自動時刻同期ではない |

設定を読み込んだ時と対象dayを変更した時に、その日の`daySeconds`をミリ秒へ変換して探索時間上限へ設定する。必要なら実行前に短い値へ変更できる。既定の締切余裕は5秒、通信timeoutは10秒である。自動送信する通常モードと担当1は、貪欲解を即時提出した後、公式回答枠の終了10秒前までを停滞探索と最終探索で共有する。停滞時と最終時はいずれも提出済みベストから改善した場合だけ送信する。手動送信する担当2・3は予行演習では20,000ms、本番の各試合では担当2が40,000ms、担当3が50,000msのプリセットから5秒の安全余裕を確保するため、実探索を約15秒／35秒／45秒にする。プロセス監視とPOST直前・レート制限待機後の締切検査も行う。時刻差は指定余裕で吸収する方式で、自動同期や受理保証ではない。確保時間が残っていなければ探索を開始しない。

SSLハンドシェイクのtimeoutが既定の10秒でも出る場合は、`timeout(s)`を15へ増やし、作業フォルダを削除せず「試合終了まで全自動」をもう一度押す。GETの公開待ちは自動再試行する。種別・回答POSTの応答が不明な場合は二重送信を避けて停止し、再開時に保存済みの同一候補だけを検査して送信する。`automatic-progress.json`や`submission-*.json`、`submitted-*.json`を削除すると安全な復旧ができない。

エージェント種別の受付終了は、設定を最初に取得した時刻と盤面幅別の受付時間（未指定時60／90／120秒）から求めて記録し、選択した試合区分の上限と`startsAt`のうち最も早い時刻を使用する。同じ設定を再取得しても延長しない。初期提出は試走なしの距離評価を使う。続く改善探索は直前に提出した構成を先頭候補として既定6候補を試走し、探索可能時間の中間点と受付終了10秒前に厳密に上回った構成だけを再送する。したがって探索上限は第1試合50秒、準決勝80秒、決勝110秒となる。

個別操作の「1a」「1b」は問題公開前から押せる。未公開中は1秒間隔で設定を再取得し、公開されたら後続処理へ自動的に進む。「停止」で待機を中断できる。認証失敗など再試行対象外のエラーは即時停止する。

自動調整が有効な場合、実際のビーム幅は状況に応じて絞られる。指定幅で比較する場合は「ビーム幅自動調整」を0にする。時間上限以下の余裕時間を設定すると、探索が即時終了する場合がある。

ローカル確認では「使用ファイル」の「開く」から`sample_maps/`の設定JSONを選び、「ローカル設定を探索」で初期状態から回答を生成できる。「実行設定・使用ファイル」のランダム設定では、寸法、台数、スポット、系列、日数、1日の秒数、チーム数を指定し、「ランダム生成して探索」で`random-setting.json`の生成から同じローカル探索まで続けて実行する。生成のたびに新しいseedを内部で選ぶため、画面にseed入力欄はない。生成可能な組合せは[`sample_maps/README.md`](../sample_maps/README.md)の3区分のみ（16×16・4台・16スポット・10〜14系列、24×24・5台・24スポット・14〜20系列、32×32・7台・32スポット・20〜28系列）で、1日の回答時間は60秒に固定する。初期値は16×16、4エージェント、16スポット、14系列、10日である。日数など本選条件が未公開の項目は従来の生成範囲を維持する。これらの操作は送信しない。生成物は`answer.json`、`score-next.json`、`result-state.json`で、最後のファイルを使って右側の状態表を探索後状態へ更新する。GUI自体は他チームの交通量を探索へ追加せず、C++ソルバーと同じく当日配布された道路状態を表示・使用する。

## ファイル

- `app.py`: Tk GUI、バックグラウンド実行、マップ描画
- `backend.py`: 通信、ソルバー起動、簡易サーバー管理、チェックポイント確定、JSON表示モデル
- `runtime.py`: macOSの対応Tkを持つPythonの検出と起動切り替え
- リポジトリ直下の`runtime/`: 取得JSON、回答、通信ログ、探索結果の照合記録。Git管理対象外

実行設定と使用ファイルは専用ウィンドウに分離し、メイン画面のボタンで表示を切り替える。実行ログは画面最下部へ横幅いっぱいに表示する。左側にはワークフローと探索結果を置き、マップ右側ではエージェントとスポットの状態を一覧できる。ワークフローと探索パラメータは固定パネルで、マップは領域に合わせて縮小する。JSONは単純な配列とオブジェクトを1行にまとめ、入れ子配列を配列単位で改行する。マップ、JSON、実行ログのスクロールバーは内容が枠を超えた場合だけ表示する。

## テスト

GUIを表示せずバックエンドを検査できる。

```sh
python3 -m unittest tests/visualizer_test.py
python3 -m unittest tests/visualizer_runtime_test.py
```

2026-10-04時点では、ランダム生成既定値、日別探索時間、JSON表示整形、現在ステップ・初期在庫の読込を含む`make test-python`の36テストが成功している。

実ソルバーを使った4日分の連携と途中日からの続行も検査する場合:

```sh
c++ -std=c++17 -O2 -pthread main.cpp -o /tmp/procon37_gui_main
PROCON_TEST_SOLVER=/tmp/procon37_gui_main python3 -m unittest tests/visualizer_test.py
```

デスクトップに接続できる環境ではGUIの操作テストも実行できる。これらのテストはHTTPをモック化し、実トークンを使用しない。

```sh
python3 tests/visualizer_gui_test.py
```

同梱簡易サーバーと実C++ソルバーでday 0の回答受理まで検査する場合:

```sh
c++ -std=c++17 -O2 -pthread main.cpp -o /tmp/procon37_simple_test
PROCON_TEST_SIMPLE_SERVER=1 \
PROCON_TEST_SOLVER=/tmp/procon37_simple_test \
python3 -m unittest tests/visualizer_simple_server_test.py
```

ランダム設定の「道路状態（ローカル探索）」で「混雑・渋滞を含める」を選べる。オフなら全道路が順調、オンなら順調・混雑・渋滞から各道路へランダムに割り当てる。地形と道路状態には、その回の生成で選んだ同じseedを使う。GUIからの再生成では、チェック設定が同じでも新しい地形・道路状態になる。生成時のseedは実行ログに表示され、必要ならCLIの`--seed`で再現できる。

道路状態は生成設定のローカル用追加項目`localTraffics`へ保存し、GUIのローカル探索では`local-state.json`としてソルバーへ渡す。初期表示・探索後表示にも同じ状態を使う。これはローカル検証用の交通条件で、実サーバーから取得した当日状態は変更しない。C++ CLIから設定ファイルだけを直接探索する場合は追加項目を使用しない。
