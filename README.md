# ゲシュタルト崩壊、うっっっこれはベンゼン環！？

六角形マップ上で巡回車と補給車を動かす競技問題の回答プログラム。C++17のソルバーがエージェント種別と日次行動を選び、Pythonのビジュアライザーと通信クライアントが回答システムとの取得・送信を担当する。

## 構成

| 場所 | 内容 |
|---|---|
| [`main.cpp`](main.cpp)、[`inc/`](inc/) | 種別選択、経路・行動探索、シミュレーション、公式JSON入出力 |
| [`visualizer/`](visualizer/README.md) | マップ表示、設定取得・種別送信、日次探索、回答送信のGUI |
| [`server_client/`](manual/server_client/README.md) | GUIを使わない取得・送信・全日自動進行 |
| [`tests/`](manual/tests/README.md) | C++・Pythonの回帰テストと計測ツール |
| [`manual/`](manual/README.md) | 実装ファイル別の使い方と詳しい操作手順 |

## GUIで試合を進める

一回戦の16×16では巡回3台の経路・在庫を同時に再配分する探索を既定で使う。系列数を優先し、燃料・日数は配布設定に追従する。[比較結果と再現手順](manual/tests/first-round-16-results-2026-10-10.md)
公開試合#1937までの16×16上位得点を目標に、通常探索完了後の最終日追加経路組合せも有効。公開12問題の対比較では系列を維持して合計5玉増加したが、全問題の上位到達は未達。[API目標と比較結果](manual/tests/arena-score-analysis-1937-16.md)
公開試合#1969の`14/108/154`を踏まえ、同じ16×16・8日・14系列では玉数優先の全車経路候補も比較する。既存計画を保持したまま全系列取得を公式リプレイで確認し、従来の系列優先候補も省略しない。保存済み実交通の全日再生では現在の探索が`14/112/172`へ改善した。`--small-board-quantity-first 0`で追加候補だけを無効化できる。[1969の検証](manual/tests/arena-score-analysis-1969-16.md)

```sh
python3 visualizer/app.py
```

1. 担当を選び、「mainを最適化ビルド」を手動で実行する。
2. 全工程を任せる場合は「試合終了まで全自動」を押す。問題公開待ちから最終日の回答送信までを継続し、「停止」後も保存済みの段階から再開できる。
3. 個別に操作する場合は「問題公開待ち・設定取得・種別選択・送信」で、公開待ち、設定取得、種別選択、種別送信をまとめて実行する。
4. 対象日の「状態公開待ち・取得・探索」を押し、日次回答をボタンで送信するか、探索後の自動送信を選ぶ。公開前に押した場合は1秒間隔で待機する。
5. 回答受理後も対象dayは維持され、日終了時刻を過ぎると次の日へ進む。手動操作では、次の日の探索を再びボタンで開始する。

全自動および「探索後に自動」では、エージェント種別は軽量な初期構成を先に提出する。日次回答は3段階で、貪欲解を即時提出し、ビームまたはSAで解の変動停止を検出した時点に提出済みベストより良ければ中間提出し、さらに公式回答枠の終了10秒前まで探索して改善していれば最終提出する。行動回答は公式の系列数・日別系列累計・玉数の辞書順で比較し、同点以下なら回答時刻のタイブレークを守るため再送しない。

接続先とTOKENは「実行設定・使用ファイル」で指定する。実サーバーへ接続せず試す場合は、同梱の簡易サーバーをGUIから起動できる。マップにはエージェントごとの経路を色分けして表示する。時計の左には直近探索の`系列数 / 総系列数 / 玉数`を表示する。詳細は[ビジュアライザーの説明](visualizer/README.md)を参照する。

接続テストは試合前10秒、エージェント選択カウントダウン10秒、タイプ回答20秒、行動回答20秒×4日で行う。問題設定と各日状態は実サーバーから取得し、送信する種別と行動だけをダミーデータにする。

3人運用では、担当1が締切10秒前を上限に停滞検出するビーム探索で問題公開待ちから最終日まで全自動、担当2が収束ビーム、担当3が収束SAで、改善時だけ手動送信する。実探索は予行演習で担当2・3とも約15秒、本番で担当2が約35秒、担当3が約45秒である。予行演習はエージェント・行動回答が各30秒、第1試合は各60秒、準決勝はエージェント選択90秒・行動回答60秒、決勝はエージェント選択120秒・行動回答60秒である。ビジュアライザは第1試合を初期選択する。試合区分を確認してから担当を選び、「mainを最適化ビルド」を押すと、`-O3 -DNDEBUG`の共通バイナリを作り、選択中の試合区分と担当の時間、`--udon-sa`設定を再適用する。探索終了後は`系列mask 玉数 日別系列累計`の3整数を画面上部に表示して候補比較に使い、採用回答が受理されたら同じ3値を口頭で伝えて他端末が1行入力する。Enterまたは「取込」で保存に成功すると入力欄は空になり、入力エラー時は修正用に値を残す。`nextDay`はGUIの対象日から自動生成し、最終日の回答後は次日がないため取込不要と案内する。端末間の有線LANファイル共有や共有フォルダの設定は不要である。運用全体は[本番運用手順](visualizer/README.md#3人で探索して口頭比較する本番運用)、引継ぎ手順は[口頭による次日チェックポイント共有](manual/spoken_checkpoint_sharing.md)を参照する。

準決勝（24×24・5台）と決勝（32×32・7台）は1人・1端末だけで実行し、口頭チェックポイント共有と追走端末は使用しない。ビジュアライザでは3人運用を「通常」にし、試合区分から「準決勝」または「決勝」を選ぶ。これによりエージェント選択は90秒／120秒、日次回答はどちらも60秒へ切り替わり、取得設定の盤面・台数・スポット数・系列数範囲も検査される。長時間SAが停滞終了した場合も、残時間があれば別乱数列・別近傍分布の独立パスを同じ実行内で比較し、系列数・日別系列数・玉数の公式辞書順で良い計画だけを採用する。[検証条件と再現手順](manual/tests/large-board-single-run-2026-10-10.md)

ローカルのランダム設定は16×16、4エージェント、16スポット、14系列、10日が初期値で、混雑・渋滞も選択できる。探索時間上限は読み込んだ設定の当日試合時間を初期値とし、実行前に短縮できる。マップ上部には日数、スポット数、重複なし系列数などを表示し、右側の表ではエージェントのP/S、位置、燃料、進行ステップと、スポット在庫の残数/初期数を確認できる。JSONタブでは単純な配列を1行、経路のような入れ子配列を配列単位で表示する。

「ランダム生成して探索」の種別選択は既定10秒以内、日次探索は表示された時間上限以内で終了する。各段階に上限+2秒のプロセス監視を設け、生成処理にも30秒の上限を設定した。初期値では種別選択と日次探索に最大約70秒を使う。

公開試合#1931までの分析に基づく玉数・必要巡回台数予測と、追加SAの訪問列引継ぎを追加した。測定条件と残る首位差は[1931までの分析](manual/tests/arena-score-analysis-1931.md)を参照する。

16×16の最終日は、既存探索の残時間で交通込みの短い在庫挿入、時刻付き給油待ち、巡回車間の末尾交換を追加比較する。混合交通・厳燃料・混雑なし20ランダムマップでは系列指標を維持して1834→1840玉だった。日別系列の最大性が未達・未証明のケースは残る。条件と生データは[共同経路改善の検証](manual/tests/traffic-aware-joint-routes-2026-10-10.md)を参照する。

## CLIで探索する

```sh
./main select setting.json agents.json
./main solve setting.json state-day0.json
./main solve setting.json state-day1.json score-day1.json
```

`select`は`POST /agent`用の種別配列を、`solve`は`POST /`用の`answer.json`と次日用の`score-next.json`を生成する。`main`自体は送信しない。day 1以降の探索には、前日の回答が受理された後に確定した得点チェックポイントが必要である。通信CLIの使い方は[クライアントの説明](manual/server_client/README.md)を参照する。

`.env`、実行ファイル、生成JSON、`runtime/`はGit管理対象外である。接続用TOKENはGitへ追加しない。

32×32・混雑／渋滞条件では、種別選択を中心補給台数から比較し、最終日に通常経路と周期再計画経路を比較する。計測結果は[種別選択改善](manual/tests/agent-selection-traffic-results-2026-10-02.md)と[経路選択改善](manual/tests/route-selection-results-2026-10-02.md)を参照する。

日次探索ではビーム探索後に系列補完、スポット再探索、巡回車ごとの経路候補組合せ、玉数ALNSを順に試す。系列補完の初回ノード上限で最大性が未確定なら、系列用締切まで上限なしで再探索し、未解決の時間を玉数専用探索へ渡さない。担当2でビーム結果が安定しても、系列上限に未到達なら同じ系列救済を済ませてから終了する。5秒以上の中間日は通常設定でも日跨ぎ候補を比較し、`--day-beam 0`で無効化できる。経路候補組合せは5秒以上の探索予算で、先行するスポット再探索後に時間が残る場合だけ実行する。候補は在庫制約を守って選び、採用前に公式シミュレータで検証する。`--route-columns 0`でこの追加探索だけを無効化できる。方式の詳細は[brain1](manual/inc/brain/brain1.md)、[日跨ぎ候補探索](manual/inc/day_beam.md)、[経路候補の組合せ探索](manual/inc/route_column_search.md)、生成問題での比較は[検証記録](manual/tests/route-column-results-2026-10-05.md)を参照する。

系列最大化後は、巡回車の末尾待機を追加店舗への経路へ置換する。経路上で取得できる系列数と店舗数を優先し、公式シミュレータで系列指標と中間日の翌日到達性を維持できた候補だけを採用する。10秒未満の短時間探索では省略し、`--terminal-wait-fill 0`で無効化できる。

公開試合#1867〜#1926とAHC上位解法の再分析を基に、焼きなましの挿入位置を前後辺だけの厳密な差分評価へ高速化した。15秒以上の自動幅ビームは目標幅の4分の1から反復深化し、長時間の独立SAは異なる近傍分布・乱数系列を比較する。翌日が当日の約3分の2以下へ短くなる場合は、一意系列の難所へ前日から接近する。条件、数値、不採用理由は[公開試合1922・1926分析](manual/tests/arena-score-analysis-1922-1926.md)、[公開試合1918分析](manual/tests/arena-score-analysis-1918.md)、[パンフレット解法分析](manual/tests/takamatsu-pamphlet-search-analysis.md)を参照する。

既定では実効探索時間を15秒未満、15〜30秒、30〜45秒、45秒以上に分け、長時間ほどビーム探索から後段改善へ時間を移す。盤面サイズに応じて玉数ALNSの試行数・1試行の展開上限も変え、最終日の30秒以上では通常近傍と3台近傍の両方に時間を予約する。固定配分との比較は`--adaptive-long-search 0`で行える。設定値と計測結果は[長時間探索の調整記録](manual/tests/adaptive-long-search-2026-10-09.md)を参照する。
